In Part 1 we went from 3,400 records using the design:

API Gateway → Lambda → DynamoDB

to 19,150 records by simply splitting the one Lambda into 2 Lambdas with an SQS in between:

API Gateway → Deserialization/Processing Lambda → SQS → DB write Lambda → DynamoDB

Simultaneously, the Lambda timeout was increased from 10 seconds to 1 min to allow lost-connection retries from the DynamoDB client.

So far, 191,500 records persisted with 1 error regarding DynamoDB connection issues is not bad. But can we do better?

Next, one more aspect is going to be changed and performance will be measured for… and that is:

  • Delivery Delay parameter in the SQS

Delivery Delay parameter in the SQS

Delivery delay specifies “a delay period from the time a message arrives on SQS to the time it is visible.”

Using Terraform we add this parameter starting from 5 seconds…

resource "aws_sqs_queue" "business_records_sqs" {
  name                      = "business-records-sqs"
  message_retention_seconds = 1209600 # Retain messages for up to 14 days (max)

  delay_seconds = 5 # delay_seconds, once delivered, delay displaying the message

  # Dead Letter Queue redrive policy
  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.business_records_dlq.arn
    maxReceiveCount     = 5 # Number of attempts before moving to DLQ
  })
}

SQS Delivery Delay = 5 sec, Lambda 2: # of workers = 10, Lambda 2 timeout = 1 min

Alright — seems like the throughput requirements were achieved. Remember originally we wanted roughly 800K records to be persisted with no errors. Notice for Lambda 2, the max number of concurrent executions was 22 and the avg time it took was 141 ms (first measurement) and 169 ms (second measurement), which is even less than 200 ms (by ~33% on avg) from the 191,500 records tried in Part 1.
