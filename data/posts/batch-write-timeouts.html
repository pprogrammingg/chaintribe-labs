BatchWriteItem accepts 25 items. That number is not a tuning knob. Chunking above it fails the call. Chunking at it is the straightforward shape of the writer, and it was the right starting size in the first Lambda.

The number that actually moved the error rate was the timeout.

With five workers and a three-second limit, 15,000 records landed with no errors, and 19,150 records lost about 22 percent. The client lost the DynamoDB connection, started a retry, and the function ended while the retry was still running. The row never got a second chance.

Raising the timeout to one minute, changing nothing else about the chunk size, brought the same 19,150-record run to zero errors. Writer latency stayed around 174 milliseconds. The extra time was almost entirely unused — except when a connection reset needed it.

A timeout should cover the failure mode you have already seen, not the happy path you hope for. Three seconds was enough for a clean write. It was not enough for a clean write plus a retry. The longer limit did not make the system slower. It made the retry visible to the function that had started it.

The later broken pipe, at 191,500 records, is the same lesson at a larger scale. A batch that fails has to return to the queue, with a receive count, not disappear into a timeout. The delay that eventually carried 786,175 records is described in part 2.
