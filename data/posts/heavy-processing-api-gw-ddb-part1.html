The constraint was blunt. Persist about 800,000 records, arriving as roughly 40 API Gateway requests, in one to two minutes. Each request could carry about 20,000 records, and those requests could land within twenty seconds of one another. Cost had to stay low. There was no extra budget for a cluster that sat idle the rest of the day.

The first design was the one most people reach for: API Gateway, one Lambda, DynamoDB.

One Lambda, ten workers

Inside that function the work was ordinary:

  1. Deserialize the body into a BusinessRecord.
  2. Split the list into chunks of 25. That is the maximum BatchWriteItem will take in one call.
  3. Write each chunk asynchronously.
  4. Inspect the result of each worker.
  5. Return success. Better error reporting was left for later, which we paid for.
let batches: Vec<Vec<BusinessRecord>> = business_record_list
    .chunks(25)
    .map(|chunk| chunk.to_vec())
    .collect();

stream::iter(batches.into_iter().map(|batch| {
    let client_ref = client;
    async move { BusinessRecord::create_batch(batch, client_ref).await }
}))
.buffer_unordered(10)
.for_each_concurrent(None, |result| async move {
    result.unwrap();
})
.await;

We never reached the concurrency argument. A single request of 20,000 records was rejected before the function ran:

HTTP/2 413 Request Entity Too Large

{ "message": "Request Too Long" }

The ceiling is payload size, not a moral limit on records. Shrinking the record got us through the door at 19,163 items. That was the new batch size for the experiment.

Four percent is not a rounding error when the next step is forty times the volume.

When the log stream is the wrong tool

The Lambda logs, read as a stream, were noisy and slow. CloudWatch Logs Insights, pointed at the same stream, was not. The query was small:

fields @timestamp, @message
| filter @message like /error/
| sort @timestamp desc
| limit 50

The errors were connection failures. Ten workers in one function were fighting for connections to DynamoDB:

DEBUG client connection error: connection error: Connection reset by peer (os error 104)

Split the function, keep the queue

A Lambda wants to be many small invocations, not one crowded one. The next design cut the work in half and put a queue between the halves:

API Gateway
  → Lambda that deserializes and enqueues
  → SQS
  → Lambda that writes
  → DynamoDB

Workers inside the writer dropped from ten to five. The tables below are the writer, not the function in front of the queue.

Twenty-five rows, and the timeout that was too polite

The chunk size stayed at 25, the BatchWriteItem limit. That number was not what moved the error rate. The timeout was.

Fifteen thousand records landed cleanly. At 19,150, about a fifth of the rows never persisted. DynamoDB refused the connection, the client retried, and the retry outlived a three-second timeout. The function died with the retry still in flight.

Five workers, one-minute timeout

19,1500%174 ms21
15,0000%176 ms15

The longer timeout was not a performance trick. It was permission for a retry to finish. Latency stayed under 200 milliseconds. We then sent ten requests of 19,150, and raised the writer back to ten workers so the fan-out would be visible.

Ten workers, one-minute timeout

191,5001 broken pipe209 ms97

One broken pipe is the kind of error that ruins a dashboard. We could not say whether that batch landed. DynamoDB has no cheap COUNT you can lean on to find a hole, and scanning the table for missing keys is not an operations plan. That is an observability problem, not a second copy of the same write loop.

Part 2 keeps this shape and changes the spacing: a delivery delay on the queue, a short random delay before each send, a cap on writer concurrency, and a single-threaded writer so a failed batch can be reported back to SQS and retried.
