In the first persistence attempt, four percent of a 19,163-record write failed. The function log, opened as a stream and scrolled by hand, did not say why. The same events, queried, did.

CloudWatch Logs is a firehose. Insights is a question you can ask it. The useful query was not clever:

fields @timestamp, @message
| filter @message like /error/
| sort @timestamp desc
| limit 50

That was enough to surface the line the stream had buried:

DEBUG client connection error: connection error: Connection reset by peer (os error 104)

Ten workers in one Lambda were resetting each other’s connections to DynamoDB. The design change — fewer workers, then a queue between a reader and a writer — came from that sentence, not from a hunch about “Lambda best practice.”

Two habits came out of it. First, a failure rate in a table is not a diagnosis. Second, a log stream is the wrong first tool when many functions are writing at once. Start with a filter and a limit. Name the error you are looking for. Then change one thing in the design, and measure again.

The broken pipe that showed up later, once, at 191,500 records, is the same class of problem. It will not be readable if the only plan is to open a stream and hope. The alarm has to name the batch. The note on spacing is part 2.
